Training an LLM

One model, many jobs

Fifteen years ago, each job had its own model, trained from zero: one to catch spam, one to tell if a review is happy, one to translate.

Each model learned language all over again. Today we learn language once, then reuse it. Reusing what a model has learned is called transfer learning.

Try it: compare the two ways.

Step 1, learning language, is called pretraining.

So how does a model learn language?

Pretraining: guess the next token

The model reads huge amounts of text and code. Its only task: guess the next token.

It starts with [BOS], a token that marks the beginning of a text. After each guess, it is shown the real next token and moves on.

Try it: step through the text. Watch how sure the model is of the real next token.

The chances are made up for this page, but they behave like a real model's: “bear” after “teddy” is easy; “Persian” is a surprise.

Going one token at a time is slow. Can we do better?

All positions at once

During training we already have the whole text. So we feed it all in at once, and the model guesses the next token at every position together.

Masked self-attention keeps it fair: each position sees only itself and the tokens before it, never the answer.

Try it: click an input to see what it can look at, and what it must guess.

🤔 Isn't training different from real use?
Yes. In training, each input is the real text, even where the model guessed wrong. This is called teacher forcing.
In real use, the model reads its own earlier words, mistakes included. Later in this lesson we'll see training that uses the model's own writing.

How do we score all those guesses?

✏️ Quick basics: the log

The chance of a whole text is all its token chances multiplied. Multiply many numbers below 1 and you get something tiny: 20 tokens at 0.5 each give 0.520 ≈ 0.000001. Computers lose accuracy with numbers that small.

The log fixes this. It turns multiplying into adding:
log(a × b) = log a + log b

Try it: move the chance and watch −log of it.
chance p

So −log p is a good “surprise” score: 0 when the model was sure and right, large when it gave the right token a small chance.

Now we can write the loss.

The loss: cross-entropy

Training wants the model to give the real text a high chance. With logs, that means a small average surprise:

loss = −1T Σ log p(right token | tokens before it)

T is the number of tokens. This is the cross-entropy loss.

Try it: train a little and watch the loss fall.
🤔 Where does this come from?
We want weights that make the training text as likely as possible:
p(text) = p(x₁) × p(x₂ | x₁) × … × p(xT | x₁…xT−1)
Take the log: the product becomes a sum.
Training likes to make things small, so flip the sign.
Divide by T so long and short texts compare fairly.

There's a catch: the loss depends on how the text was cut into tokens.

Comparing models with different tokenizers

Two models can cut the same text into different numbers of tokens. Then their cross-entropy is an average over different T, so the numbers don't compare.

Bits per byte fixes this. It shares the loss over the text's bytes (letters, spaces, dots), which don't depend on the tokenizer:
BPB = loss × TB × 1log 2

Try it: switch tokenizers. Both models are equally good here.

B is the number of bytes. Dividing by log 2 turns the log's units into bits.

What text does the model read?

What the model reads

Pretraining text comes from three main places: the web (pages and Wikipedia), code (GitHub, Stack Overflow), and maths and science.

The mix matters a lot. How much code? How much maths? Good data often helps more than a better model design.

Try it: open each source.

🤔 How do people choose the mix?
Training a huge model many times would cost too much. So people train many small models, each on a different mix, and see which does best.
Then they guess the best mix for the big model from those results.

And how much of it?

How much text?

Trillions of tokens. GLM-5, an open model from 2026, read about 30 trillion.

Sometimes we run out of good text. Is reading the same text again worth it? A 2023 study says yes, up to about 4 times: almost as good as new text. After that, each extra pass helps less and less.

Pretraining was once the whole first step. Now there's a second.

Midtraining

After pretraining, many models get midtraining: more next-token guessing, but on better text that matches what we want the model to be good at, like reasoning or code.

It also teaches the model to read much longer texts.

Try it: which stage would read each text?

Why is reading long texts something to teach?

Teaching longer texts

Pretraining uses short windows, about 4,000 tokens, because it's cheaper. RoPE turns each query and key by an angle that grows with position, like clock hands at different speeds.

The slow hand only ever turned a little during training. At position 16,000 it points somewhere the model has never seen.

Try it: move to a far position, then squeeze the slow hand.
position

🤔 Why is long-context training hard?
Cost. Every token looks at every other: 32 times more tokens means 1,024 times more pairs.
Data. We need texts where a word near the end really depends on something far back. Those are rare.

Methods like YaRN squeeze the slow hands. Then the window grows step by step: 4K → 32K → 128K → 1M tokens.

After all that, what do we have?

What pretraining costs, and what it can't do

💸 Cost

Millions of dollars at least, weeks of time, and a lot of electricity.

📅 Knowledge cutoff

The model knows only what was in its text, up to the day it was collected.

✏️ Hard to edit

A wrong fact is spread across billions of weights. You can't just fix one line.

📋 Copying

It can repeat text it read, word for word.

How do we turn it into a helpful assistant?

Supervised fine-tuning

To change how the model behaves, we show it examples of the behaviour we want. Each example is a pair: an input and the output we'd like for it.

This is supervised fine-tuning, or SFT. For an assistant, the pairs are instructions and good answers. Teaching that is called instruction tuning.

Try it: look at four example pairs.

The training is still next-token guessing, with one change.

What changes?

Learning only the answer

The instruction is given to the model. We don't want it to learn to write instructions, only answers. So only the answer tokens count in the loss:

loss = −1T Σ log p(answer token | instruction, answer so far)

Here T counts only the answer tokens.

Try it: compare with pretraining, where every token counts.

🤔 How is this different from midtraining?
Midtraining still reads plain text and guesses every token. It's just better text.
Fine-tuning reads input–output pairs and learns only the outputs. It changes behaviour, not knowledge.

What data, and how much?

After fine-tuning

SFT data can be written by people or made by other models: chats with an assistant, all kinds of instructions, maths and code, and safe answers to risky requests.

It's small next to pretraining: thousands to millions of examples, against trillions of tokens. But it must be very good, because the model copies it exactly.

Fine-tuning has a cost: changing billions of weights needs a lot of memory and big machines.

Do we really need to change all of them?

✏️ Quick basics: big tables from small ones

A column of 4 numbers times a row of 4 numbers gives a 4 × 4 table: each cell is its row's number times its column's number.

That's 16 numbers made from only 8. Such a table is called low-rank.

Try it: change the dashed numbers.

The bigger the table, the bigger the saving. A 4,096 × 4,096 table has about 16.8 million numbers; one column and one row have 8,192.

Now we can make fine-tuning cheap.

LoRA: change a little, not everything

The pretrained model is almost there. So we freeze its weights W₀ and learn only a small change, built from two thin tables B and A:

W = W₀ + B × A

This is LoRA. B is d × r, A is r × d, and r is small. Results are often about as good as changing everything.

There's another nice side to this.

One model, many small add-ons

Take the three jobs from the start: spam, reviews, translation. With LoRA we keep one copy of W₀ and a small B and A for each job. Swapping B and A swaps the job.

Try it: switch jobs and compare storage.

For a general assistant, one big model does everything. LoRA shines for very specific jobs.

Which tables get B and A?

Where to put LoRA

Each Transformer layer has tables in attention (WQ, WK, WV, WO) and in the feed-forward network (W₁, W₂).

The first LoRA paper put B and A on attention only. Today the advice is to use them everywhere, especially in the feed-forward network, where most weights are.

Try it: compare the two choices.

Fine-tuning shows the model what to do. Can it learn what not to do?

Teaching what not to do

Even a fine-tuned model can give a bad answer. SFT only ever showed it good examples; it never said “not like this”.

So we collect preference pairs: one prompt, a better answer and a worse one. Then we train the model to prefer the better one. This is preference tuning.

Try it: which answer is better?
Suggest a new activity I could do with my teddy bear.

🤔 Why pairs?
Comparing is easy. Writing the perfect answer is slow and hard.
SFT is fragile. Its data must be perfect and well spread; it's hard to get much of it.
A bad answer is also a hint to check the SFT data for mistakes.

Pairs aren't the only way to collect preferences.

Three kinds of preference data

Say we have four answers to the same prompt. We can mark them in three ways:

Pointwise: a score for each answer. Pairwise: which of two is better. Listwise: a ranking, best to worst.

Try it: see the same four answers in each form.

Pairwise is used most: easiest for people. The pairs come from the fine-tuned model's own answers, marked by people.

✏️ Quick basics: the sigmoid

The sigmoid squashes any number into a chance between 0 and 1:
σ(x) = 11 + e−x

Very negative x gives nearly 0. Zero gives exactly 0.5. Very positive x gives nearly 1.

Try it: move x.

Now we can turn two scores into a chance.

The reward model

A reward model reads a prompt and an answer, and gives one number: the answer's reward. Higher means better.

It learns from pairs with the Bradley–Terry rule. The chance that answer i is preferred over answer j is:
p(i better than j) = σ(ri − rj)

Try it: set two rewards.
rA
rB

Only the difference matters. Equal rewards give 50–50.

How does the reward model learn its rewards?

Training the reward model

For each pair, we want the winner's reward above the loser's. Like before, we take the chance of what really happened, log it and flip the sign:

loss = −log σ(rwinner − rloser)

Try it: train on the six pairs from the four answers.

In practice: about 10,000 pairs marked by people (the “human feedback”). The reward model is often an LLM with its next-token layer swapped for a one-number output.

Now we use the reward model to train our LLM.

Chasing the reward, but not too far

The LLM writes answers to about 100,000 prompts. The reward model ❄ (frozen) scores each one, and the LLM 🔥 (being trained) changes its weights to get higher rewards. This is reinforcement learning. Together with the reward model, it's RLHF.

But the reward model isn't perfect. So the goal also keeps the LLM close to where it started, the fine-tuned model:
goal = reward − β × distance from start

Try it: change β. Which answer wins?
β

RLHF needs a reward model and tricky training. Is there a simpler way?

DPO: no reward model needed

DPO trains on the preference pairs directly. It uses the same loss as the reward model, with a special reward: how much more likely the LLM now makes an answer than the starting model did.

r = β log pnow(answer)pstart(answer)

Try it: train on one pair, the movie-night answer over the stay-away one.

β = 0.5 here. To shrink the loss, the winner must get more likely and the loser less likely.

How can a model get better at working things out?

Thinking before answering

Chain of thought showed it: a model answers better when it writes its reasoning first. But we had to ask for it, with examples in the prompt.

A reasoning model is trained to do it by itself. Its output is reasoning, then answer. The reasoning is usually hidden, but you still pay for every token of it.

Try it: change the thinking effort.
The bear was born in 2020. How old is it now?
It's 6 years old.

🤔 Why hide the reasoning?
Privacy and safety. It can repeat private details from earlier in the chat.
Copying. Good reasoning text can train other models, so companies keep it to themselves.

OpenAI showed the first such model in September 2024. DeepSeek-R1 (January 2025) was the first open one to explain how.

How do we train a model to reason?

Rewards you can check

For maths and code, we don't need a reward model. We can check the answer: compare it with the known right answer, or run tests on the code.

So the reward is simple: is the answer right? And did it reason first, inside <think>…</think>?

Try it: check each answer to “born in 2020, how old now?”. The right answer is 6.

For code, the check is a set of tests: the code gets the reward if every test passes.

How does the model learn from these rewards?

GRPO: compare answers in a group

GRPO asks the LLM to answer the same question several times. Each answer gets its reward. Then each is compared with the group:
advantage = reward − group average

Above average: write more like that. Below: write less like that. And like RLHF, don't drift too far from the starting model.

Try it: make the model answer 6 times.
🤔 Is that the whole formula?
Almost. GRPO also divides by how spread out the rewards are, so every question pushes about equally hard.
The full maths comes with reinforcement learning, next.

There are two kinds of training signal. Let's put them side by side.

Off-policy and on-policy

Two questions describe any training method. Who wrote the text it learns from: someone else (off-policy) or the model itself (on-policy)?

And how detailed is the feedback: a mark for every token (dense), or one reward for the whole answer (sparse)?

Try it: place each method.

Can we fill the empty corner?

On-policy distillation

The model being trained, the student, writes an answer. A stronger teacher model then marks every token: how likely would it have written that token itself?

The student is pushed toward the teacher's choices. The text is the student's own (on-policy), and the feedback is per token (dense). This is on-policy distillation.

Try it: compare the two kinds of feedback.

🤔 What if there's no stronger teacher?
Self-distillation: the same model plays teacher, but it is shown the right answer first, so it knows where to steer.
Many teachers: one expert in maths, one in coding, and so on. The student learns from each.

Pretraining and midtraining fill their windows in different ways.

Packing text into windows

Training reads text in fixed-size windows. Documents have all sorts of lengths. How do we fill the windows?

Concatenate and chunk (pretraining): join all documents end to end and cut every window full, even mid-document. Best-fit packing (midtraining): fit whole documents where they fit best, and fill the gaps with [PAD].

Try it: pack 7 documents into windows of 8 tokens.

There's one more danger in the data itself.

Model collapse

The first LLMs read text written by people. Today, much of the web is written by AI.

Train on AI text, and the model learns from a finite sample of another model's writing. Rare words and ideas get missed, and once missed, they are gone for good. Repeat this, and the model collapses into a dull, narrow version of language.

Try it: each generation learns only from 60 words written by the one before.

What matters most

📚 Pretraining

Guess the next token over trillions of tokens. The model learns language, code and facts, up to a cutoff.

🧑‍🏫 Fine-tuning

Input–output pairs teach behaviour, with loss on the answer only. LoRA makes it cheap.

⚖️ Preferences

Pairs teach what's better. RLHF uses a reward model; DPO skips it.

Checkable rewards and GRPO teach the model to think before it answers.
